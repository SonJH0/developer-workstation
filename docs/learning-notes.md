# 내가 한 일과 설명 연습

## 작업 순서

1. Windows 환경을 확인했다. WSL·Ubuntu를 설치해 Linux 명령을 실행할 기반을 만들었다.
2. jaehyeong 계정과 Linux 홈 아래 프로젝트 폴더를 만들었다. script로 명령·출력 기록을 남겼다.
3. 파일을 생성·복사·이동·삭제하고, 파일과 디렉토리의 권한을 각각 변경했다.
4. Docker Desktop을 설치하고 Ubuntu와 연동했다. 기존 세션의 그룹 권한이 갱신되지 않은 문제를 새 로그인 쉘로 해결했다.
5. hello-world로 이미지 다운로드와 컨테이너 실행을 확인했다. Ubuntu 컨테이너 내부에서 ls·echo 등을 실행하고 CPU·메모리를 조회했다.
6. exec 쉘만 종료하는 경우와 주 프로세스가 종료되는 경우를 비교했다. 중지한 컨테이너를 다시 시작했다.
7. NGINX 베이스에 내가 작성한 HTML을 COPY하는 Dockerfile을 만들고 웹 서버 이미지를 빌드했다. 8080:80 포트 연결로 브라우저에 접속했다.
8. 호스트 폴더를 바인드 마운트해 Version 1을 Version 2로 수정하고 재빌드 없이 반영되는 것을 확인했다.
9. 볼륨에 파일을 저장하고 컨테이너를 삭제한 뒤 다른 컨테이너에서 같은 파일을 읽었다.
10. 포트 중복 오류를 의도적으로 재현하고 호스트 포트 변경으로 해결했다.
11. Git 작성자와 기본 브랜치를 설정하고 첫 커밋을 만들었다. VS Code를 WSL과 연결하고 GitHub 비공개 저장소에 게시했다.
12. 실습 로그와 캡처를 근거로 README·트러블슈팅·재현 자료를 정리했다. 추가 재현 스크립트를 사용자 PC에서 실행해 COPY와 바인드 마운트 차이, 볼륨 데이터 유지, 정리 후 종료 코드 0을 확인했다. GitHub 최종 업로드 검증은 별도 단계다.

## 1분 설명 예시

Windows에 WSL과 Ubuntu를 설치해 Linux 개발 환경을 만들었습니다. 터미널에서 파일 관리와 권한 변경을 실습하고 결과를 로그로 남겼습니다. Docker Desktop을 Ubuntu와 연결한 뒤 컨테이너 실행·중지·재실행과 주 프로세스의 생명주기를 확인했습니다. NGINX 이미지에 직접 만든 HTML을 넣은 커스텀 이미지를 빌드하고 포트 매핑으로 브라우저 접속을 확인했습니다. 바인드 마운트로 호스트 변경 반영을, 이름 있는 볼륨으로 컨테이너 삭제 후 데이터 유지를 검증했습니다. 마지막으로 Git과 GitHub로 결과물과 이력을 관리했습니다.

## 예상 질문

| 질문 | 내가 확인한 결과로 답하기 |
|---|---|
| 이미지를 왜 만드는가? | HTML과 서버 환경을 함께 묶어 같은 방식으로 실행할 수 있다. 베이스 태그가 바뀌는 한계도 문서에 적었다. |
| EXPOSE만 적으면 접속되는가? | 아니다. 실행 시 -p로 호스트 포트와 컨테이너 포트를 연결했다. |
| exit하면 항상 컨테이너가 종료되는가? | exec로 연 별도 쉘 종료는 주 프로세스에 영향을 주지 않았다. bash가 주 프로세스인 컨테이너는 종료됐다. |
| 8080과 80은 무엇인가? | 8080은 내 컴퓨터에서 접속한 포트, 80은 컨테이너의 NGINX 포트다. |
| 바인드 마운트와 COPY의 차이는? | COPY는 빌드 시 파일을 이미지에 넣는다. 바인드 마운트는 실행 시 호스트 경로를 연결해 변경이 보인다. |
| 영속성을 어떻게 증명했는가? | 첫 컨테이너를 삭제하고 같은 볼륨을 연결한 새 컨테이너에서 기존 문장을 읽었다. |
| 권한 오류는 어떻게 해결했는가? | 등록된 그룹과 현재 세션의 그룹을 비교한 뒤 다시 로그인해 반영했다. |
| 커밋과 push의 차이는? | 커밋은 로컬 이력 저장, push는 원격으로 그 이력을 전송하는 작업이다. |
| 내 기여는 무엇인가? | 안내를 받아 내 PC에서 명령을 실행하고 결과를 관찰·기록했다. 생성된 코드와 문서를 사용했으며 각 명령의 목적과 실제 출력으로 결과를 설명한다. |

위 문장을 외우기보다 logs와 이미지를 열어 어떤 출력이 각 설명의 근거인지 연결해 본다.
